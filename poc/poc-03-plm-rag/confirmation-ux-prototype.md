# POC-03 人工确认待办交互原型

## 定位与边界

当前 R2 工作簿属于 POC-03 Golden Dataset 技术评审，不是项目交接过程中由技术协议、合同或方案分析产生的正式业务待办清单。它的目标是验证检索测试数据能否被人工确认，因此暴露了来源类型、分类枚举、引用定位等技术字段。

R3 将用户反馈转换为 Phase 0 交互原型，用来验证更适合正式交接场景的确认方式。它不冻结正式数据模型、API Contract 或业务界面，也不把 AI 建议变成项目事实。

## 用户问题与改进原则

|用户问题|R3 改进|
|---|---|
|主表塞入大段原文，难以阅读|主表只显示问题、风险、AI 发现、需确认事项、AI 建议和处理结果。|
|无法快速找到证据|每条记录提供“打开证据”，跳到同目录的本地证据定位器。|
|不知道人工要维护什么|“需要您确认什么”按问题类型给出明确说明；人工输入列使用黄色背景和受控选项。|
|技术字段和业务确认混在一起|原 R2 技术评审表完整保留为底层审计页，主表只承担业务确认。|
|AI 结论容易被误认为事实|AI 建议持续标明“仅为建议”，只有人工决定才能改变状态。|

## R3 主清单

主清单字段为：

1. 待办编号、问题类型和风险等级。
2. AI 发现、需要用户确认的具体事项和 AI 建议。
3. “打开证据”链接。
4. 人工处理结果、补充说明或修改后结论。
5. 原审核状态、审核人、审核时间和当前状态。

人工处理结果限定为：

- 同意 AI 建议；
- 修改后确认；
- 需要补充资料；
- 不构成待办；
- 退回 AI 重分析。

当资料类型缺失时，提示必须明确为：填写“标准能力、合同、技术协议或调研”；如果均不适用，填写“不适用”并说明原因。不得为了通过 Gate 自动伪造来源类型。

## 证据定位行为

R3 工作簿与 `evidence-navigator.html` 必须保存在同一目录。点击“打开证据”后，浏览器跳转到对应候选编号，展示：

- 来源文件名和脱敏文档编号；
- 精确页码、段落、表格、幻灯片或形状定位；
- 与该问题相关的证据上下文；
- “打开原文件”按钮。

当前 PoC 能力边界：PDF 可携带页码打开；DOCX、PPTX 等 Office 文件可打开原件，并在证据卡中显示精确段落、表格或幻灯片定位。正式产品应使用内置 Evidence Viewer，根据 `DocumentVersionId + SourceLocator` 自动跳转并高亮原文，避免依赖本机文件路径或 Office 客户端行为。

## 正式交接模块建议流程

```text
交接资料分析
  → AI 发现 AnalysisItem
  → 人工查看证据并确认/修改/驳回
  → 经确认后生成 ActionItem
  → 指定负责人、截止时间和验收标准
  → TraceLink 反向追溯文档版本与定位
```

正式 `ActionItem` 至少应包含项目、问题类型、风险、正式结论、处理动作、负责人、截止时间、验收标准、状态、来源文档版本、来源定位、确认人和确认时间。AI 发现和正式待办必须是两个状态明确、可审计的对象。

## 本轮验证结果

- R2 共 120 行，人工均填写为 `APPROVED`，审核人和日期已保留。
- 45 行满足当前 Golden Dataset 必填 Gate。
- 75 行仍缺来源类型，R3 标为“待补充”并给出具体维护提示。
- 120 条记录均生成本地证据链接，120 个原文件路径均已解析。
- 工作簿与证据定位器只保存在 Git 忽略的本地 `artifacts/`，未上传客户内容或提交 Git。

## 后续冻结条件

在 Architecture Freeze、Data Model Freeze 和 API Contract Freeze 前，不实现正式业务模块。进入正式设计时，必须单独确认：

1. AnalysisItem 与 ActionItem 的状态机和转换权限。
2. 不同文件格式的定位与高亮协议。
3. 人工必填规则、条件必填和退回 AI 的重分析策略。
4. TraceLink、DocumentVersion 与审计记录的正式数据模型。
5. 客户内容、AI 调用和本地文件访问的权限边界。
