# POC-03 独立留出集真实质量复验失败分析 R10

## 结论

2026-09-21 在 Windows 11、PostgreSQL 18.6、pgvector 0.8.6 上完成 50 条独立留出集真实复验。Top-5 Recall 为 49/50（98.00%），达到 95% 门槛；分类准确率为 24/50（48.00%），低于 90%；精确来源引用准确率为 37/50（74.00%），低于 98%。POC-03 总体保持 `FAIL / BLOCKED_QUALITY_GATE`。

R10 本地分层诊断确认：主要问题不是 Embedding、数据库、Reranker 或模型调用失败，而是分类任务输入与人工标签语义不闭合，以及引用选择过度依赖候选顺序；同时，严格的可接受引用集合存在潜在漏标。当前结果与门槛均不修改。

## 链路完整性

- 2,056 个唯一 Chunk 与 50 个查询完成 2,106 个真实 Embedding 向量缓存。
- 50/50 条百炼 `qwen3-rerank` 真实重排完成。
- 50/50 条 DeepSeek `deepseek-flash` Prompt v2 预测完成。
- PostgreSQL GIN 与 pgvector HNSW 均实际命中。
- 缺失预测 0，越界引用 0，ProjectId 和来源类型隔离保持启用。
- 首次数据库装载发现 17 个重复 ChunkId、22 行冗余记录。核验确认全部逐字段相同；修复只合并完全一致记录，同 ID 不同内容继续失败关闭。

## 分层诊断

### 1. 分类任务与证据输入不闭合

- 合同、调研、技术协议共 17 条，检索命中 16 条、精确引用命中 13 条，但分类只命中 1 条。
- 其中合同 0/7、技术协议 0/8；标准能力资料为 23/33。差异说明问题集中在“需求/约定证据如何转换为标准、部分、非标或资料不足结论”，而不是通用模型完全无法理解资料。
- 当前 SQL 按 `source_type` 限制候选来源。合同或技术协议问题只能看到同类需求/约定证据，无法同时取得标准能力证据进行对照。
- Prompt v2 把“现有标准能力或明确约定满足问题”并列为 `STANDARD_SATISFIED` 条件；但人工标签表达的是能力适配结论。明确写入合同或技术协议，只能证明“存在该要求”，不能证明“标准能力已满足”。
- 当前问题文本中又存在“合同/协议是否明确要求、是否记录”等文档事实问法，进一步诱导模型回答条款是否存在，而不是执行能力差异分析。

因此，人工标签保持有效，但模型任务合同缺少“问题类型 + 需求证据 + 标准能力对照证据 + 判定依据”四项闭环输入。

### 2. 模型明显偏向 `STANDARD_SATISFIED`

- 人工标签中 `STANDARD_SATISFIED` 为 23 条，模型预测 44 条。
- `STANDARD_SATISFIED` 召回为 22/23；`INSUFFICIENT_INFORMATION` 仅 1/13；`NON_STANDARD` 为 0/10；`PARTIALLY_SATISFIED` 为 1/3；`NO_RELIABLE_MATCH` 为 0/1。
- Prompt v2 没有要求先把复合需求拆成原子条件并逐项核对，也没有给出非标、资料不足与部分满足的结构化正反例。模型只要找到相关肯定描述，就容易直接落入“标准满足”。

### 3. 引用选择存在显著首位偏差

- 50 条中有 46 条引用了候选第 1 名。
- 正确证据位于第 1 名时，引用命中 35/37；正确证据位于第 2～5 名时，只命中 2/12。
- 13 条精确引用失例中，11 条选择了第 1 名。现有 Prompt 要求引用“最直接”的 Chunk，但没有逐候选支持度比较输出，实际行为接近默认引用第 1 名。
- 这说明 Top-5 已经足够时，仍需要独立 Evidence Selector，而不能把“排序第一”直接等价为“最精确证据”。

### 4. 可接受引用集合存在潜在漏标

- 13 条精确引用失例中，8 条被模型引用的 Chunk 包含全部人工 `expected_answer_terms`，另有 4 条包含部分术语；5 条位于人工期望 Chunk 的同一文档。
- 这不自动证明模型引用正确，也不授权修改本轮金标；但它证明未来数据集不能只登记一个代表性 Chunk，必须在模型运行前完成人工可接受引用集合与近重复证据审查。
- 当前 74.00% 严格结果继续冻结，不做事后补标，不据此追溯修改本轮分数。

### 5. 非主要原因

- 不是外部服务失败：Embedding、Reranker、DeepSeek 调用均完整。
- 不是缺失或越界输出：两项均为 0。
- 不是总体检索不足：49/50 已命中；只有 1 条属于最终 Top-5 检索失例。
- 不是上下文字符截断：Chunk 上限 900 字符，Prompt 单 Chunk 上限 1,000 字符。
- OCR 乱码和字符间空格仍是资料质量风险，但合同/技术协议的大多数引用已命中，因此不是本轮分类 48% 的首要原因。

## Root Cause

1. `P0`：能力适配标签需要跨来源对照，但现有检索只提供同来源证据。
2. `P0`：Prompt v2 混合了“条款存在”和“标准能力满足”两种不同任务。
3. `P0`：引用输出没有独立候选支持度判定，形成 46/50 的首位引用偏差。
4. `P1`：人工数据只登记代表性引用，未完整覆盖语义等价或重复证据。
5. `P1`：复合需求没有原子条件覆盖矩阵，部分满足、资料不足和非标边界不稳定。

## 修复方案

### 方案 A：双阶段证据与判定链（推荐）

1. 在独立开发/校准集上为问题增加 `question_type`：文档事实确认或能力适配判断；最终五类质量 Gate 只评估定义清晰的能力适配任务。
2. 能力适配任务同时装配两组证据：需求/约定证据与标准能力证据；继续强制 ProjectId 隔离，但不再把同一 `source_type` 当作唯一候选域。
3. Prompt v3 先输出匹配性、充分性、原子条件覆盖和非标正向依据，再映射到五类结论；不得把“合同明确要求”直接映射成“标准满足”。
4. 增加独立 Evidence Selector，对 Top-5 每个候选的直接支持度进行比较，再选择引用；候选顺序只能是特征，不能代替支持度判断。
5. 数据集冻结前完成人工可接受引用集合审查，将语义等价 Chunk、重复文档 Chunk 和必要的相邻 Chunk 一并登记；运行后禁止补标。
6. 当前 50 条只作为回归诊断集；修复在独立开发集完成后，使用全新独立留出集按 95% / 90% / 98% 原门槛复验。

### 方案 B：只修改 Prompt 并增加少量示例

实现较快，但无法解决合同/技术协议缺少标准能力对照证据、引用集合漏标及首位引用偏差，预计只能降低部分 `STANDARD_SATISFIED` 误判，不足以稳定达到 90% / 98%。不推荐作为最终方案。

### 不采用

- 不降低质量门槛。
- 不修改本轮人工标签或事后扩充引用集合以抬高分数。
- 不在本轮 50 条上逐条编写规则。
- 不因本次失败直接更换 DeepSeek、Embedding、Reranker、数据库或总体架构。

## 处理决定

1. 冻结本轮 98.00% / 48.00% / 74.00% 结果。
2. 接受方案 A 作为下一轮离线修复设计方向，但尚未执行新的外部模型调用。
3. 本轮 50 条继续作为已见回归诊断集，不再用于“独立未见集通过”声明。
4. 任何新客户数据外发、全新留出集真实调用或正式 Gate 仍按现有规则单独确认。
