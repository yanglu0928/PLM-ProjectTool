## 决定的事务顺序

1. 外层Plan SubmitReview Owner验证命令与幂等Key，在UoW内取得可信Session Actor、License与ProjectManager授权；锁定并核验所有Reviewer，预留业务幂等Receipt。
2. 调用`ProjectReviewPersistenceService.submit_in_transaction`。Plan Subject `authorize_create`先锁Plan身份/当前版本集合，仅接受最新DRAFT且Review指针为空；通用Review根与首轮均由既有Review仓储写入同一Session。
3. Start Subject在相同事务和实际行锁下调用P05-P04只读Proof，复评固定版本及当前Approved Solution/来源；Review/Round已插入但未commit时，`finalize_start`只更新PlanVersion白名单Review状态列并追加0190 `START`结果事件。
4. 统一Review组件检查活动Subject绑定并写`REVIEW_CREATED`/`REVIEW_STARTED` Audit；外层Owner完成同事务201 Receipt，再由其UoW唯一提交。任何失败须整体rollback。
5. 同Key重放只重建已保存的SubmitReview结果并重新检查当前访问，不重复创建Review/Round或写新状态事件；不得重跑Proof来改写首次结果。

锁顺序以既有Outline submit-review Owner为参照：先Reviewer集合与Project授权，后Plan身份/PlanVersion集合，最后Review/Round；Review和Plan身份不是由不同事务交错持有。当前Plan创建也是先锁Plan identity再插版本。数据库0190的延迟约束仅在最终提交点核验START事件与PROJECT/PLN-02 Review、Round、Actor事实闭合。
