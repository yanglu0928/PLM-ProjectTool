# CR-PRJ-006：成员创建的安全用户候选解析

日期：2026-09-28；状态：依据 CR-EXEC-001 持续授权，记录后可执行；范围：Phase2 `PRJ-05-A07-P03` 成员创建页面前置。不回写 Gate2 原冻结提交 `64cdf09`。

## 冲突与证据

冻结 `PROJECT_MEMBER_CREATE` 要求当前 ProjectManager 提交目标 `user_id` 与 `department_id`。现有 `AUTH_USER_LIST` 固定为 DeploymentAdmin 专用，项目负责人不能读取；现有成员历史列表只包含已加入者，不能提供新成员候选。前端若直接要求输入 UUID，会把内部标识暴露为主要操作入口，不能满足非技术用户的成员创建流程。部门 GET 已有 Project member 权限，但前端尚未接线。`PRJ-05-A07-P01/P02` 只证明传输与响应合同，不证明页面可用。

## 方案比较与选择

- 不选复用 `/api/v1/admin/users` 或扩大其权限：会让 ProjectManager 获得整个部署用户目录，改变冻结安全边界。
- 不选通过成员历史猜新用户、让浏览器遍历 UUID 或要求管理员转交 UUID：无法发现目标，且易泄露/误配。
- 选择新增只读、精确用户名解析 API，限当前有效 ProjectManager 且复核 Session、License、项目当前权限；只返回单个启用用户的最小 `user_id` 与显示名，未命中/不符合资格统一安全结果，不回传其他项目归属。对输入长度、字符、请求频率和响应缓存设限；不修改原 `AUTH_USER_LIST` 或 `PROJECT_MEMBER_CREATE`。项目部门仍用现有 Project Department GET，由前端只展示 ACTIVE 选项。页面最终写入仍由原 POST 服务端重新核验，候选结果不是授权或资格证明。

## 差异、风险、迁移与回滚

这是冻结 `/api/v1` 的**非破坏性新增端点**，需补增量 API 合同、权限矩阵和测试；不更改原冻结文件、实体或 Schema。主要风险是精确用户名枚举、跨项目权限旁路、候选过期与前端错误展示。实施前具体定义速率限制及统一未命中语义；若现有安全设施不能满足，停止公开接线并记录阻塞。回滚撤新增端点/前端候选选择器，旧 POST 与管理目录保持不变；无数据迁移。

## 验证计划与边界

先完成 `P03-A01` 后端最小候选解析/权限与增量合同（含真实 PostgreSQL 当前负责人、普通成员、部署管理员非成员、跨项目、停用/已分配/缺失用户、会话与许可、限流/缓存安全）；`P03-A02` 前端部门 ACTIVE 列表与候选客户端；`P03-A03` 页面按用户名/角色/部门显式确认、原 Key 未知结果恢复。之后独立实际浏览器/PG 写链。不能用合成 UI 测试宣称生产信任/发行或 Gate3 通过；Windows Server 2025/Debian 13 与正式信任材料仍按 Release Gate 管理。
